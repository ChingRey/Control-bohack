# Teaching Agent 聊天记忆：调研与接入方案

日期：2026-11-13。**本文保留原始设计供对照；部分内容已经接入。** 当前实现与实际验证见[MEMORY_IMPLEMENTATION](MEMORY_IMPLEMENTATION.md)。消息表迁移、通用记忆纠错/恢复和跨项目检索尚未实现；以下拟定表结构与API不能全部视为已上线。

## 1. 建议选什么

优先验证 **LangMem 的摘要与结构化记忆提取＋现有 SQLite**。保留当前 Teaching 调用和后端，只增加可替换的记忆模块，不先把整套服务改成 LangGraph 或 Letta。

下面区分官方已有能力与我们的设计判断；这些工具不能直接证明学生掌握情况。

| 现成技术 | 已查证的能力 | 对我们的用途与限制 |
|---|---|---|
| LangMem | 提供摘要、结构化记忆提取、自定义Agent接入；函数式提取接口由应用控制存储 | 首选实验对象：整理长对话，输出受约束的教学记录；仍要自行校验引用、管理版本和入库 |
| LangGraph | 区分会话状态与跨会话记忆，支持数据库持久化和历史摘要 | 借鉴状态与记忆分开；当前不需要为了记忆立刻重写流程编排 |
| Letta | 当前Agent SDK使用文件式记忆；部分记忆常驻上下文，其余按需读取；记忆有Git版本 | 借鉴“简短总记录＋按需查阅详细记录”；完整迁移会改变现有Agent运行方式 |
| Mem0 | 从对话提取信息、按范围检索，并提供显式更新和删除 | 可用于后续跨项目偏好和经验检索；不是直接拿来判定学生能力的成绩册 |

依据：[LangMem介绍](https://langchain-ai.github.io/langmem/)、[结构化提取](https://langchain-ai.github.io/langmem/guides/extract_semantic_memories/)、[自定义Agent接入](https://langchain-ai.github.io/langmem/guides/use_tools_in_custom_agent/)、[LangGraph记忆](https://docs.langchain.com/oss/python/langgraph/add-memory)、[Letta当前记忆机制](https://docs.letta.com/agent-sdk/memory)、[Mem0添加](https://docs.mem0.ai/core-concepts/memory-operations/add)、[更新](https://docs.mem0.ai/core-concepts/memory-operations/update)、[删除](https://docs.mem0.ai/core-concepts/memory-operations/delete)。

**接入成本要实测。** LangMem函数式API可与自有存储配合，但安装包仍依赖LangChain、LangGraph等库；不是只加一个无依赖小函数。先在独立虚拟环境做适配实验，再决定是否引入主项目。[官方依赖声明](https://github.com/langchain-ai/langmem/blob/main/pyproject.toml)

## 2. 当前机制的问题

现在每轮发送最近50条两侧对话、最多最近80条学生发言，再补部分旧证据；不同区域可能重复。按条数截取不能限制总长度，最近几轮教学结果也可能携带重复内容。

已有course摘要和目标记录，但没有明确标出“哪些原话已经整理、哪些还没整理”，缺少独立的记忆版本与纠错流程。聊天与修改历史仍放在整个任务JSON内，持续增长会增加读写负担。

需要分别解决：**原话怎么保存、旧话怎么整理、本轮读什么、教师判断怎样追溯。** 单纯换成向量数据库解决不了全部问题。

## 3. 记住什么，各自谁负责

| 记录 | 保存内容 | 更新者与可信范围 |
|---|---|---|
| 原始对话与操作 | 学生、Coding、Teaching原话；计划确认；文件改动和代码版本 | 后端记录实际事件；保留角色、时间、项目和来源编号 |
| 项目进度 | 确认计划、执行到哪步、最近改动、尚待验证事项 | 执行事实由后端读取；“已经完成/测试通过”不能由摘要模型自行填写 |
| 教学接续 | 讨论过什么、学生卡在哪里、讲解过什么、下一步接着做什么 | 模型整理，标为教师笔记，不自动当作事实或学生能力证明 |
| 学生表现 | 在什么情境下解释了什么、有无提示、能否设计验证、是否完成新情境作答 | 每一条挂接原始作答与代码版本；只能形成有范围的观察或待复核建议 |
| 学习偏好 | 学生明确选择的选学主题、希望详细还是简洁 | 优先保存学生明确表达，不从一次表现推断永久能力标签 |

例：记录“学生在提示后指出应先trim，原话m42，尚未解释为什么”，不能压缩成“学生已掌握输入校验”。“教师讲过”也不能记成“学生学会”。

学生表现至少包括：objective_id、observation、evidence_message_ids、help_given、verification_kind、code_hash、observed_at、review_status。verification_kind区分聊天解释、学生自述、静态检查和真正运行的测试。

## 4. 每次交互怎样走

### 第一步：先保存原话和项目事件

学生在任一聊天框发送消息，后端先持久化，给出稳定message_id和项目内递增seq，再确认接收。确认执行、代码变更也有对应版本。

两个聊天渠道共用项目编号，但保留channel和role。不能把Coding或Teaching的解释当作学生作答证据，也不把聊天文本变成系统指令。

### 第二步：判断是否需要整理旧对话

根据**待整理内容的token量**和项目检查点触发，不是每条都重新总结全部历史。初始实验可在未整理内容约4000 tokens，或一项讨论结束时触发；这是待测试参数，不是库的默认保证。

借用LangMem的running summary思路，只处理新增的、已结束的消息段；保留近期原话。源消息区间、摘要版本和处理策略版本一并记录。摘要与原始聊天分开保存，聊天界面仍显示原话。[官方摘要示例](https://langchain-ai.github.io/langmem/guides/summarization/)

对每段旧对话保存独立小结；项目总记录由有效的小结、结构化观察和后端进度整理。避免只剩一段反复改写的总摘要，后面无法找回遗漏。

### 第三步：为当下问题组织材料

教师每轮主要读取：**当前学生问题＋最近一次给Coding的提示词原文＋当前计划与相关代码＋简短项目记录＋少量近期原话＋相关旧证据**。

当前提示词单独放置，带message_id、所属步骤和代码版本，不埋在旧聊天中。提示词分析关注：目标与范围是否明确、验收是否具体、限制是否一致、是否考虑当前工程；必须引用原话，并说明仍需追问什么。

不能凭提示词长、术语多或一次生成成功，就推断学生掌握了技术。学生自己能否解释原因、预测结果和设计验证，要另看作答证据。

旧证据先按同一学生、项目、知识点、代码版本筛选，再按相关性挑选。第一版可先做结构化查询；确实出现跨项目语义检索需求，再对比Mem0或向量检索，不先引入额外服务。

### 第四步：教师回复，同时提出记忆更新草稿

教师看到材料后给出引导、讲解或总结；同时产生教学接续和学生表现的结构化草稿。结构化输出参考LangMem的自定义schema提取方式；应用保留是否写入的控制权。[提取接口](https://langchain-ai.github.io/langmem/guides/extract_semantic_memories/)

后端检查字段、来源消息、角色、原话引用、代码版本和允许的状态变化；通过后才能形成新版本。引用存在只证明出处存在，不证明教育判断正确。能力观察不直接触发加分或安装Skill。

### 第五步：后台整理完成后，下轮加载新记忆

普通整理放后台，优先保证消息先接收、回复可见。整理失败继续保留旧记忆和未处理消息，不推进“已整理到哪里”的游标，并允许重试。

如果未整理内容已经大到本轮预算放不下，明确显示“正在整理历史”，先补齐必要片段；不能悄悄跳过中间对话，却假装教师都看过。每次运行记录实际加载的消息编号和记忆版本。

## 5. 每轮能放多少

下面是**实验起始预算**，不是当前已实现参数，也不是模型最大上下文。总输入暂按约16000 tokens规划，另留约3000 tokens输出；部署时还须验证所选模型的实际窗口。

| 材料 | 初始token预算 |
|---|---:|
| 教师规则与选中的Skill | 2000 |
| 项目进度与教学接续记录 | 2000 |
| 当前Coding提示词、学生当前问题 | 3000 |
| 与当前步骤有关的源码 | 4500 |
| 近期原始对话 | 2000 |
| 检索到的旧证据 | 1000 |
| 工具定义及余量 | 1500 |

优先保留当前问题、当前提示词和必要源码；超过某一分区预算时可借用其他分区，仍超总预算则要求拆分或先查阅相关片段，不静默截断。已检索的消息不再在近期聊天中重复注入。

tokens不是汉字数。DeepSeek适配实验必须验证计数方法；暂用估算时明确标记，并用API返回的usage做校准。每轮记录输入量、输出量、记忆量、调用次数和延迟，工具结果也计算在内。

## 6. 后台存储、版本与导出

**继续用SQLite。数据库保存结构化记录，Markdown只是给人看的导出，不让数据库和文档各自维护一份真相。**

在兼容迁移设计中保留现有tasks和teaching_history；建议新增三个职责明确的表：

| 表 | 最少字段与职责 |
|---|---|
| messages | message_id、task_id、seq、channel、role、content、created_at、code_hash；原话可分页读取 |
| memory_versions | memory_id、revision、task_id、kind、body_json、source_ids、source_range、code_hash、status、supersedes、created_at；保存小结、接续、学生观察等版本 |
| memory_jobs | job_id、task_id、from_seq、to_seq、expected_revision、policy_version、status、attempts、error；追踪整理和重试 |

同一memory_id的旧版本保留，新版本通过supersedes指出替代关系；纠错或撤销会改变“本轮允许加载的有效版本”，不直接覆盖历史。不同项目的学习记录不能因相似关键词混在一起。

### 稳定性需要明确做到

- 每次成功提交，把新记忆、当前有效版本和整理任务状态写在**同一个事务**内；不能先标整理成功，再发现记忆没保存。SQLite支持事务，但事务外的文件与模型请求不会因此自动一致。[SQLite事务说明](https://www.sqlite.org/lang_transaction.html)
- 以项目、消息区间和策略版本设置幂等键，同一个整理任务重试不重复写。
- 摘要计算在事务外做，提交时检查expected_revision；冲突后重读合并，不拿旧快照覆盖当前进度。消息区间可以存历史小结，但不能用旧区间把当前事实改回去。
- 来源范围必须精确。中间一段未处理不能把总游标越过去；有缺口就记录缺口。
- 学生纠正事实时保留纠正来源；对“我已经学会”记录自述，不直接覆盖原来的掌握证据。
- 项目代码变更后，旧观察仍属历史；当前的通过状态或能力建议需要按新版本重新核实。
- 撤销记忆后，之后的摘要与检索不能再次带入已撤销内容；真正删除个人数据还要覆盖原话、派生摘要、索引和导出，不能只给记忆加无效标记。
- 记忆中的代码和对话仍是不可信材料，不能提升为系统规则；不存密钥，不给记忆提取器任意文件或网络权限。

### Markdown学习记录长什么样

导出一个项目一份记录：项目目标、确认计划、实际完成进度、讨论过的知识、学生表现与原话编号、未解决问题、下一步、最近提示词反馈、记忆版本与时间。

“系统记录的事实”“模型整理的笔记”“待复核的学生能力判断”分开标注。导出时从数据库生成，避免文档过时后又被当成最新事实传回模型。

### 现有数据怎么迁移

先备份数据库，并保留旧消息数组下标到新message_id的映射；已有学生证据和前端引用不能随意改编号。逐任务核对消息数、角色、内容哈希和代码文件后，再切换读取方式；通过前不删除旧字段。

这个迁移不能和摘要算法一次性无验证地上线。第一步可先读取旧格式、验证新记忆模块，待通过后再迁移消息存储与分页。

## 7. 模块与接口怎么留

以下均为**拟新增**，不是已经可调用的接口。

| 模块 | 输入 → 输出 | 谁拥有写权限 |
|---|---|---|
| memory_builder | 待整理消息段、原记忆、事件与来源编号 → 更新草稿 | 模型只返回草稿 |
| memory_store | 校验后的草稿、expected_revision → 新版本或冲突 | 后端事务 |
| context_builder | 当前问题、提示词、计划、代码、相关有效记忆、预算 → 实际模型输入与清单 | 只读 |
| learning_record_export | 项目编号 → Markdown | 只读生成 |

建议页面接口：GET任务下的 `/memory` 查看；GET `/memory/export` 导出；POST `/memory/:memory_id/correct` 提交纠正；GET `/messages?cursor=…` 分页原话。纠正也要有确认和依据，不提供模型随意覆盖全部记忆的入口。

## 8. 接入前如何证明比现在好

先在独立实验中使用同一组对话比较：现有截取方式、LangMem普通滚动摘要、加入教学字段与证据检查的方案。

| 测试 | 必须检查什么 |
|---|---|
| 连续100–200条，Coding聊天占多数 | 当前提示词原文仍在；能回答做到哪里，不重新开课 |
| 学生最早提出的关键约束 | 摘要保留它，并能回到原话；不是只记最近一句 |
| 教师讲过但学生未回答 | 不变成“学生掌握”；不能误触发升级 |
| 学生改口、项目规则改变 | 新记录生效，旧约束不继续被当成当前规则 |
| 修改代码、切项目 | 旧代码结论标明过期，不跨学生/项目泄漏 |
| 摘要超时、重复提交、进程重启 | 原话不丢、旧记忆可用、任务能重试且不重复记 |
| 人工纠错与撤销 | 下一轮不再加载错误记忆，历史可追溯 |
| 压力与费用 | 记录token、重复注入量、延迟、检索命中；不是只看界面能否回复 |

先验证DeepSeek与LangMem的模型适配、结构化输出和token计数，再选定依赖版本。真实教学判断需要人工核对；官方教程提供的是接法，不是我们系统有效性的证明。

特别注意：[Mem0的AI Tutor教程](https://docs.mem0.ai/cookbooks/companions/ai-tutor)展示了存储和获取记忆，但其ask示例没有把检索记忆注入本次生成。不能仅照抄它就声称教师已经利用长期记忆，更不能据此证明掌握判断准确。

## 9. 推荐执行顺序

1. 独立环境跑通LangMem摘要与自定义教学schema，保持现有工作台可用。
2. 用固定长对话验证来源编号、当前提示词保留、摘要遗漏和错误掌握判断。
3. 验证SQLite版本提交、失败重试和纠正后不再加载；通过后接入context_builder。
4. 再迁移消息表与分页，最后增加学习记录查看、导出和纠错入口。

原始实施原则：先隔离验证再接入。后续已完成的范围及限制以MEMORY_IMPLEMENTATION.md为准。
