# Control 第二版：教学策略试点任务卡

## 目的

用一个范围固定的待办应用输入检查任务，跑通“策略 V1 教学 → 保存证据 → 生成候选策略 → 人工审核 → 新任务验证 → 启用或回退”。本任务只验证教学策略闭环，不代表系统已证明教学效果，也不实现 Coding Agent Skill 的安装。

## 选择依据与边界

- 项目：Control 工作台内置的「我的待办」教学示例。
- 教学入口：工作台“教学示例”按钮创建的独立预置项目。
- 主问题：表单提交时没有先清理并检查输入；空字符串或仅空格可能创建看不见内容的待办。
- 本轮不考核：刷新后的数据持久化。预置示例也包含该遗漏，但它是另一个学习目标，先作为后续任务，不与输入验证混在同一评分里。
- 不使用“角色落地后再次跳跃”作为本项目任务：该仓库的项目是待办应用，没有游戏或跳跃逻辑。
- 不直接使用 `data/workbench/` 中已有用户任务作为教材起点；每次试教通过内置示例创建独立任务，保留现有本机数据。

## 任务定义

| 字段 | 定义 |
|---|---|
| task_id | `todo-empty-input-validation` |
| task_version | `1`（首次试点；正式冻结时补充生成项目快照的文件哈希） |
| project | 我的待办静态网页，`index.html`、`style.css`、`app.js` |
| learner_goal | 学生能根据实际现象定位输入验证问题，解释空白字符串为何不应创建待办，并提出可检查的修复要求和验证办法 |
| task_start | 由内置“教学示例”生成的预置审查项目；不要先执行示例中的预设修复步骤 |
| out_of_scope | localStorage 持久化、完成状态、视觉样式和代码风格优化 |

## 固定复现步骤与预期

1. 在空白待办列表中提交 `买牛奶`：创建一条可见待办。
2. 提交空字符串：观察是否产生空白项目。
3. 提交只含空格的字符串（例如三个空格）：观察列表及代码，判断是否产生不可见或仅含空格的项目。
4. 不告诉学生修复代码；要求其指出相关输入处理依据，并提出正常输入与边界输入的验证办法。

基线预期：预置审查版本的提交处理直接使用原始输入值，没有执行去除首尾空白并拒绝空结果的逻辑，因此可能接受空白内容。该行为以试点时生成的预置项目源码及浏览器实际观察为准；若实现已变更，应更新任务版本和复现说明，不能沿用旧结论。

## 策略 V1：分级引导

1. **先独立观察**：请学生预测并实际比较正常输入、空输入和纯空格输入；先不透露问题位置。
2. **追问证据**：请学生说明观察到的结果，并指出输入值从表单到列表的处理过程。
3. **按需给提示**：
   - 级别 0：只追问现象和判断依据。
   - 级别 1：提示比较正常值、空值和纯空格值。
   - 级别 2：提示检查表单提交处理中的输入读取和条件判断。
   - 级别 3：解释首尾空白处理和空值检查的概念，但仍不提供当前任务完整修复代码。
4. **学生提出方案**：要求学生用自己的话说明修改要求及至少两种验证输入；Coding Agent 修改前需由学生确认。
5. **检查结果**：检查正常待办是否仍可添加，以及空/纯空格是否被拒绝。标明这是对当前项目行为的检查，不将源码标记存在当作行为通过。
6. **独立迁移**：教学后另行提出昵称输入情境，学生需独立说明正常输入和纯空格输入的预期结果及验证办法；不要先给提示或答案。

## 评分记录（用于试点分析，不自动加分或解锁）

每项记 0、1 或 2 分，并保留原始回答和评分理由，总分 0–10。分数是分析字段，不单独代表掌握。

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 现象判断 | 未指出空白输入问题 | 识别空输入或纯空格中的一种 | 能区分并解释两种边界输入 |
| 代码依据 | 没有依据 | 指出提交处理但解释不完整 | 能说明原始输入如何进入列表及缺少的判断 |
| 修复要求 | 没有可执行建议 | 建议处理空白但规则含糊 | 清楚表达先规范输入、再拒绝空结果的要求，不依赖照抄代码 |
| 当前任务验证 | 没有检查方法 | 只提出正常输入或边界输入检查 | 覆盖正常、空字符串和纯空格输入，并说明预期结果 |
| 独立迁移 | 没有作答，或答案依赖提示 | 能答对部分情境，但关键判断依赖提示或理由不足 | 无提示地迁移到昵称情境，说明正常和纯空格输入的预期及验证方式 |

评分时另外记录每个关键判断得到的最高提示级别、是否独立完成、任务版本和策略版本。普通聊天、教师讲解后的复述不能登记为独立迁移证据。

## 新任务迁移题

> 昵称输入框只输入空格后提交，你认为系统应该怎样处理？请说明正常昵称和纯空格昵称各自的预期结果，以及你会怎样验证。

此题与待办任务考查相同的输入边界判断，但领域表面不同。只有学生单独提交的作答才进入迁移评价；若题目或评分规则改变，提升迁移任务版本。

## 每次会话必须记录

- `task_id`、任务版本、项目文件快照哈希、预置项目来源。
- 策略系列 ID、策略版本 ID、策略正文哈希。
- 教学模型/提供方模式、模型名（如可用）、提示模板版本。
- 前测或初始表现、教学事件顺序、学生原始回答、提示级别。
- 当前任务结果、迁移题版本与原始回答、Rubric 各项分数及理由。
- 候选策略、引用的会话证据 ID、审核人和审核理由、试用分配方式、启用/回退决定。

操作停留时间等交互遥测只作辅助，不推断理解。模型评分需要保留解释并支持人工复核；试点阶段不自动发经验值、不自动解锁 Skill。

## V1/V2 比较约定

- V2 必须针对明确观察到的教学困难提出一项具体变化，不要一次改动多条提示规则。
- 使用未见过的新任务验证迁移，任务难度和评分规则尽量匹配；记录学生初始表现和所用策略版本。
- 若参与者较少，结果只用于发现问题和决定是否继续试用，不宣称统计证明 V2 更有效。
- 候选先经人工批准进入试用；试用记录完整后再由负责人决定启用、继续试用或放弃。
- 启用和回退只改变后续会话所选版本，不修改旧版本或历史会话。

## 第一轮验收

- 能从工作台创建独立的待办教学示例，不覆盖已有任务。
- 三种输入的复现步骤、观察记录和项目快照可以复查。
- Teaching Agent 按 V1 分级引导，不直接泄露当前练习的完整修复。
- 迁移作答由学生明确提交，并与普通聊天区分。
- 会话可追溯至任务版本、策略版本、提示过程和迁移结果。
- 当前系统已有的 `candidate` / `pending_review` 只作为建议状态，不被描述成已掌握、已升级或已证明策略有效。

## 代码依据（试点开始时复核）

- `agents/teaching.py` 已定义 `input-validation` 目标、空白昵称迁移题和评分维度。
- `agents/coding.py` 的教学预置步骤包含不做空白输入处理的提交逻辑；后续步骤会写入固定示例修复。
- `backend.py` 的“教学示例”入口创建独立任务并载入预置审查版本；因此试教时不要执行该固定修复步骤。
- 当前版本的 Teaching Agent 有会话内连续教学记录和待复核升级申请，但没有跨会话策略版本、候选审核、对照试用和回退闭环。
